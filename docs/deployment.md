# Размещение и эксплуатация сайта Total Stream

Версия 1.0. Дата: 13 октября 2026 года. Инструкция предназначена для разработчика и администратора VPS. Она описывает целевую конфигурацию; команды на реальном сервере в рамках подготовки документации не выполнялись.

Сайт работает как статическая сборка Astro за Nginx. Основное [техническое задание](technical-spec.md) определяет интерфейс, контент и приёмку. Домен, контакты и параметры VPS будут предоставлены позже.

Подготовка локальных инструментов, настройка реального VPS и публичный выпуск — отдельные задачи T06, T11 и T12 в [плане разработки](development-plan.md). Их состояние фиксируется в [очереди задач](task-board.md).

## 1. Состав инфраструктуры

| Компонент | Решение |
| --- | --- |
| VPS | Один сервер; стартовый ориентир 1 vCPU, 1 ГБ RAM, от 10 ГБ диска |
| ОС | Поддерживаемый Ubuntu LTS, точный выпуск выбрать при настройке |
| Веб-сервер | Nginx из поддерживаемого источника пакетов |
| HTTPS | Let’s Encrypt, автоматическое продление через Certbot или другой ACME-клиент |
| Сборка | CI или рабочая машина; в production передаётся готовый артефакт |
| Staging | Отдельный виртуальный хост и каталог на том же VPS |
| Доступ | Административный SSH по ключам, отдельный пользователь публикации |
| Резервирование | Репозиторий, артефакты релизов и копия конфигурации вне VPS |

Ресурсы VPS — исходный ориентир для статического сайта без размещения тяжёлого видео. После запуска проверять трафик, свободное место и время ответа. Доступность зависит от одного VPS; автоматического переключения на второй сервер нет.

## 2. Каталоги на сервере

```text
/var/www/total-stream/
  releases/
    <release-id>/       # Полное содержимое dist/ конкретной сборки
      index.html
      404.html
      _astro/
  current -> releases/<release-id>
  shared/
    _astro/            # Хешированные ресурсы нескольких релизов

/var/www/total-stream-staging/
  releases/
  current -> releases/<release-id>
  shared/_astro/

/etc/nginx/sites-available/total-stream
/etc/nginx/sites-available/total-stream-staging
```

`release-id` состоит из времени сборки и короткого SHA коммита. Релиз после загрузки не изменяется. Nginx читает файлы, пользователь публикации записывает релизы и переключает ссылку. Права на чтение файлов и проход по каталогам выдаются явно; режим 777 не используется.

Папка `shared/_astro/` нужна для вкладок, открытых до выпуска нового HTML: старые URL скриптов, стилей и изображений продолжают работать. В неё добавляются только ресурсы с хешами в именах, без перезаписи содержимого по существующему URL. При совпадении имени и различии байтов выпуск останавливается.

## 3. Подготовка VPS и домена

1. Установить системные обновления, Nginx и выбранный ACME-клиент. Создать пользователей и каталоги.
2. Разрешить публичные порты 80 и 443. SSH ограничить административным доступом. Порт приложения не нужен.
3. Настроить A-запись основного домена на IPv4 VPS. AAAA добавлять только при рабочем IPv6 и соответствующих правилах сети.
4. Если используются основной домен и `www`, выбрать один канонический адрес. Для каждого HTTPS-имени получить действующий сертификат; альтернативный адрес перенаправлять на основной.
5. Создать отдельное имя staging, закрыть HTTP Basic Auth и исключить его из индексации.
6. Сначала поднять HTTP-конфигурацию с доступным ACME challenge, затем получить сертификат и включить HTTPS. Не ссылаться в Nginx на ещё не созданные файлы сертификата.
7. Включить автоматическое продление и проверить его тестовым запуском выбранного клиента. После продления Nginx должен перечитать сертификат.

Конкретные имена и пути сертификатов заполняются при настройке; вымышленные домены не переносятся в production.

## 4. Требования к Nginx

Корень сайта — `/var/www/total-stream/current`. Для `/` отдаётся `index.html`. Для неизвестных маршрутов — настоящая ошибка 404 и `404.html`; SPA-перенаправление всех адресов на главную запрещено.

| Запрос | Ответ |
| --- | --- |
| Основной HTTPS-адрес `/` | 200, главная страница |
| HTTP-адрес | 301 или 308 на канонический HTTPS, кроме ACME challenge |
| Альтернативный домен | 301 или 308 на основной домен с сохранением пути и query |
| Неизвестный путь | 404 с содержимым `404.html` |
| Отсутствующий ресурс | 404, без долгого кеширования |
| `/_astro/*` | Файл из `shared/_astro/`, только существующие ресурсы |
| Скрытые файлы, исходники и секреты | Недоступны; в релиз включается только dist/ |

Внутри HTTPS server block используется `try_files $uri $uri/ =404;` для обычных путей и `error_page 404 /404.html;`. Для `/404.html` задать отдельный internal location, чтобы содержимое ошибки отдавалось с исходным статусом 404. Не применять конструкцию `error_page 404 =200 ...`. Семантика описана в [Nginx core module](https://nginx.org/en/docs/http/ngx_http_core_module.html#try_files).

Для хешированных ресурсов `/_astro/` задать отдельный location с сопоставлением к shared-каталогу и проверкой существования файла. Перед включением проверить реальный JS, CSS и изображение: корректный код, MIME и тело ответа.

### Кеширование

| Ресурс | Cache-Control |
| --- | --- |
| HTML | `no-cache` |
| Хешированные ресурсы `/_astro/` с ответом 200 | `public, max-age=31536000, immutable` |
| Файлы с неизменяемым именем: favicon, robots, sitemap | `public, max-age=300` |
| Ошибки и staging HTML | `no-store` |

`immutable` применяется только к именам, меняющимся вместе с содержимым. Изображения и шрифты по возможности проходят через сборку и получают хеши. Для незахешированных файлов нельзя задавать годовой кеш.

Настроить MIME-типы, gzip для текстовых ресурсов, запрет листинга каталогов и заголовок `X-Content-Type-Options: nosniff`. Учесть наследование `add_header`: собственные заголовки в location могут отменять набор родителя; проверить фактические ответы каждого класса ресурсов. См. [Nginx headers module](https://nginx.org/en/docs/http/ngx_http_headers_module.html).

На staging добавить `X-Robots-Tag: noindex, nofollow` ко всем ответам. Basic Auth — реальное ограничение доступа; robots.txt не является защитой.

Полный конфиг формируется при получении домена, путей сертификатов и проверки версии Nginx. Перед каждым изменением выполнять `sudo nginx -t`; только при успешной проверке — `sudo systemctl reload nginx`. При простой смене ссылки на релиз reload не требуется.

## 5. Контракт сборки

В package.json реализованы команды `check`, `build`, `test:e2e` и `format:check`. `build` сначала проверяет данные окружения, затем собирает Astro и проверяет dist. Локальные e2e сейчас проверяют preview; перед выпуском T10 дополняет их сценариями финальных контактов и production SEO. Инструменты поставки и точные команды находятся в [infra/README.md](../infra/README.md).

Последовательность в чистом окружении:

```sh
pnpm install --frozen-lockfile
pnpm format:check
pnpm check
BUILD_CONTEXT=production SITE_URL="$TS_SITE_URL" pnpm build
pnpm test:e2e
```

`TS_SITE_URL` заранее задаётся реальным каноническим HTTPS-адресом. При отсутствии переменной или контактов production-сборка останавливается. Проверки Playwright должны запускать локальный сервер готовой сборки через конфигурацию `webServer`.

Для staging использовать `BUILD_CONTEXT=preview` и его собственный URL. Staging-сборка содержит noindex и не переносится в production без пересборки. Публиковать production-артефакт из того же проверенного коммита и lockfile; после пересборки повторить проверки метаданных и smoke-сценарии.

Артефакт включает dist/, SHA коммита, версии Node и pnpm, режим сборки и контрольную сумму архива. Инструменты разработки, исходники, `.git` и `.env` на публичный веб-корень не загружаются. Astro описывает размещение статической сборки в [руководстве по deploy](https://docs.astro.build/en/guides/deploy/).

## 6. Выпуск

1. Запустить проверки и сборку. Убедиться, что получены `index.html`, `404.html`, SEO-файлы и все связанные ресурсы.
2. Проверить preview на staging. Для production собрать артефакт с правильным доменом и повторить проверки окружения.
3. Получить блокировку публикации, чтобы два выпуска не выполнялись одновременно. Сохранить путь текущего релиза для отката.
4. Загрузить новый релиз в отдельный временный каталог; сверить контрольные суммы и права, затем переименовать в окончательный `releases/<release-id>`.
5. Добавить хешированные ресурсы в `shared/_astro/` без удаления старых. Проверить отсутствие коллизий имён.
6. Проверить ссылки HTML на ресурсы, отсутствие заглушек и корректность домена до переключения.
7. Создать временную символьную ссылку на новый релиз и атомарно заменить `current` в пределах одной файловой системы.
8. Проверить сайт по реальному HTTPS-адресу. При ошибке вернуть предыдущую ссылку и повторить проверки.
9. Записать результат выпуска: release-id, SHA, время, ответственный, результаты smoke-проверки. Снять блокировку.

Пример переключения на Ubuntu после проверки существования релиза и при удерживаемой блокировке; `TS_RELEASE_ID` должен быть заранее задан проверенным идентификатором:

```sh
TS_SITE_ROOT=/var/www/total-stream
test -n "$TS_RELEASE_ID" || exit 1
test -f "$TS_SITE_ROOT/releases/$TS_RELEASE_ID/index.html" || exit 1
test ! -e "$TS_SITE_ROOT/current.next" || exit 1
test ! -L "$TS_SITE_ROOT/current.next" || exit 1
ln -s "$TS_SITE_ROOT/releases/$TS_RELEASE_ID" "$TS_SITE_ROOT/current.next" || exit 1
mv -Tf "$TS_SITE_ROOT/current.next" "$TS_SITE_ROOT/current"
```

Флаг `-T` относится к GNU coreutils на целевом Linux. Это фрагмент процедуры, а не готовый скрипт деплоя: получение блокировки, загрузка, журнал и проверки реализуются отдельно. Переключение не должно выполняться при незавершённой загрузке файлов.

## 7. Откат и хранение релизов

При нарушении доступности, повреждённых ресурсах, ошибках контактов или неверном окружении вернуть `current` на ранее записанный релиз тем же атомарным способом. Shared-ресурсы не удалять. Если проблема вызвана конфигурацией Nginx, восстановить предыдущую конфигурацию, выполнить `nginx -t` и reload.

Хранить минимум пять последних релизов. Общие хешированные ресурсы хранить минимум 30 дней и обязательно сохранять всё, на что ссылаются текущий и сохранённые релизы. Очистку проводить отдельно от публикации по списку используемых ресурсов. Вкладка старше срока хранения может потребовать обновления страницы.

Артефакты и конфигурации сохранять вне VPS. При утрате сервера: подготовить новый VPS, восстановить Nginx и сертификаты, развернуть последний рабочий артефакт, проверить сайт, изменить DNS. Время восстановления зависит от провайдера и DNS; гарантированное SLA пока не задано.

## 8. Проверки после выпуска

- Главная возвращает 200 по HTTPS, сертификат действителен для домена.
- HTTP и альтернативное имя перенаправляют на правильный адрес без циклов.
- Случайный несуществующий путь возвращает 404, а не главную с кодом 200.
- JS, CSS, шрифты и изображения нового релиза загружаются с правильным MIME.
- Ресурс предыдущего релиза из `/_astro/` продолжает открываться.
- Контакты и меню работают на телефоне; исходный HTML содержит основной контент.
- Production не содержит noindex и staging URL; canonical и sitemap корректны.
- Staging запрашивает пароль и остаётся закрытым для индексации.
- HTML перепроверяется, хешированные ресурсы имеют долгий кеш, ошибки не кешируются надолго.

## 9. Эксплуатация

Предусмотреть внешнюю проверку доступности каждые 5 минут с уведомлением после двух последовательных сбоев, проверку срока TLS-сертификата и предупреждение за 14 дней до истечения. Канал уведомлений назначает владелец сервера при настройке.

Следить за свободным диском и доступностью сайта внешними HTTP-проверками. По решению пользователя журналы запросов проекта отключены: access_log off; сообщения error_log виртуальных хостов направляются в /dev/null, поскольку они тоже могут включать IP. Это относится к HTTP/ACME, основному HTTPS-хосту, алиасам и staging. Диагностика отдельных запросов по журналам недоступна. Перед размещением проверить nginx -T и nginx -t, отсутствие повторного включения логов во вложенных location/include и настройки default_server, TLS, reverse proxy/CDN, хостинга и системных журналов. Проектные шаблоны не управляют логами сторонних сервисов и глобальными сообщениями до выбора виртуального хоста. Если существовали старые логи/копии, они не удаляются этой правкой: срок хранения и удаление согласовать отдельно. Это техническая минимизация данных, а не юридическая гарантия отсутствия обработки персональных данных.

Ответственный за VPS устанавливает обновления безопасности и проверяет автоматическое продление сертификата. После изменения Nginx, DNS, правил сети или сертификатов повторяется проверка доступности. Периодически проверяется восстановление из сохранённого артефакта.

## 10. Что уточнить при размещении

Потребуются провайдер и параметры VPS, основной домен, наличие `www`, staging-имя, доступ к DNS, способ запуска CI и ответственный за эксплуатацию. Доступы передаются через защищённый канал или секреты CI; они не включаются в документацию и репозиторий.

Настоящая инструкция не создаёт сервер, не регистрирует домен и не публикует сайт. Конфигурация будет проверена на выбранной инфраструктуре в этапе размещения.
