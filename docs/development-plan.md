# План разработки Total Stream для агентов

Версия 1.1. Дата: 13 октября 2026 года. План превращает [техническое задание](technical-spec.md) и [инструкцию размещения](deployment.md) в задачи для оркестратора и исполнителей. Пользователь поручил реализацию; актуальный ход работ и приёмка находятся в [доске задач](task-board.md).

## 1. Цель и три результата

Собрать адаптивный статический лендинг Total Stream на Astro, TypeScript и CSS в фиолетово-лаймовой айдентике. Кейсы располагаются на главной. Все действия связи ведут к контактам; форм, API и CRM нет. Публикация — на собственном VPS с Nginx.

| Результат | Что означает | Что допускается оставить незаполненным |
| --- | --- | --- |
| G1 Готов локальный preview | Все секции и взаимодействия реализованы, сборка и локальные проверки пройдены | Реальные контакты, домен, кейсы, окончательные медиа и шрифты; ограничения явно перечислены |
| G2 Готово к публикации | Подставлены реальные материалы, production-сборка проверена, VPS и HTTPS подготовлены | Только необязательные блоки, которые скрыты |
| G3 Опубликовано и проверено | Проверен реальный HTTPS-адрес, зафиксирован релиз, проверена процедура отката | Невыполненных обязательных условий запуска нет |

G1 не означает, что финальный дизайн проверен с отсутствующими шрифтами и фотографиями. G2 и G3 нельзя объявлять на основании локального preview. Сейчас необходимые внешние данные намеренно отложены; задачи до G1 выполняются без повторного запроса контактов и домена.

## 3. Роли и управление работой

| Роль | Ответственность |
| --- | --- |
| Оркестратор и интегратор | Очередь, контракты, общие конфиги, зависимости, композиция страницы, приёмка результатов |
| Агент интерфейса | Дизайн-система или назначенная группа секций |
| Агент контента | Схемы, данные, реестр материалов, проверка готовности контента |
| Агент поставки | Локальные шаблоны Nginx, выпуск, откат и эксплуатационные проверки |
| Независимый QA | Пользовательские сценарии, адаптивность, доступность, отчёт о дефектах |

Это роли, а не пять одновременно работающих агентов. При четырёх слотах один занимает оркестратор, одновременно работают не более трёх исполнителей. После окончания задачи слот переиспользуется. Проверяющий не должен быть единственным автором проверяемой реализации.

Состояние работы хранится в [доске задач](task-board.md), а не только в переписке. Статусы: `queued` → `active` → `review` → `done`. `waiting_external` применяется только к задаче, готовой продолжиться после конкретных внешних данных; `needs_changes` возвращает результат на исправление. `done` выставляет оркестратор по критериям задачи, а не по сообщению агента «готово».

Использовать подагентов текущего задания. При наличии инструментов оркестрации: `spawn_agent` для первого назначения, `send_message` для уточнения активного задания, `followup_task` для следующей задачи завершившему работу агенту, `list_agents` для состояния и `wait_agent` для ожидания. Не запускать частый опрос без изменений. Новые пользовательские указания передаются затронутым исполнителям и фиксируются на доске.

В общем workspace файлы видны всем сразу. Агент не редактирует файл, которым в этот момент владеет другой исполнитель.

| --- | --- |
| `AGENTS.md`, доска, план, общие решения | Оркестратор |

| `src/content/*`, `src/data/*`, `src/content.config.ts`, `src/assets/images/*` | T03, позже явно передаются T10 |
| `src/lib/content.*`, `scripts/validate-release.mjs`, тесты валидатора | T03; интерфейсы определены T01 |
| `src/components/sections/SiteHeader.astro`, `Hero.astro`, `Contacts.astro`, `SiteFooter.astro` в том же каталоге; `src/scripts/navigation.ts` | T04 |
| `src/components/sections/Services.astro`, `Cases.astro`, `Reliability.astro`, `Process.astro`, `FAQ.astro`, `Trust.astro`, `Reviews.astro` в том же каталоге | T05 |
| `infra/*`, `scripts/deploy/*` | T06, позже T11 |
| `tests/e2e/*`, `tests/fixtures/*`, отчёты QA | T08; тесты и fixtures валидатора T03 лежат отдельно в `tests/validation/*` |
| `src/scripts/reveal.ts`, сборочная интеграция и SEO | Оркестратор в T07 |

Каждый исполнитель пишет только собственный `docs/reports/TXX.md`. Оркестратор устанавливает пакеты по заявке исполнителя и не запускает установку одновременно со сборкой. Разрешён только один процесс, перезаписывающий общий `dist/`; независимые проверки получают отдельные каталоги вывода. Не форматировать весь репозиторий во время параллельных изменений.

Worktree не обязательны. Если изоляция необходима, сначала создать исходный коммит с нужными файлами, затем выделить агенту ветку и checkout. Только оркестратор интегрирует изменения и разрешает конфликты. В общем checkout агенты не переключают ветки и не делают собственные массовые коммиты.

## 6. Контракт до параллельной работы

T01 оформляет `docs/contracts.md` и минимальные типы; T02 и T03 не изменяют интерфейсы независимо друг от друга.

- Якоря: `top`, `services`, `cases`, `process`, `contacts`. Секция владеет своим `id`; реестр навигации единственный. Дублирующиеся `id` запрещены.
- `Container` принимает семантический тег и содержимое; `ButtonLink` — href и вариант primary/secondary/text; `SectionHeading` — заголовок и необязательную подпись. Точные TypeScript-интерфейсы фиксирует T01.
- Секции получают данные через props. Загрузка, сортировка и фильтрация находятся в одном модуле контента. UI не читает произвольные JSON и переменные окружения напрямую.
- `published` означает редакторский допуск, а не автоматическое доказательство достоверности. Реестр материалов хранит источник, статус утверждения и права использования.
- Отсутствующие отзывы и логотипы скрываются. Если кейсов пока нет, preview сохраняет `#cases` с нейтральной подписью о подготовке материалов; вымышленные проекты не подставляются.
- Preview по умолчанию безопасен: незаданный `BUILD_CONTEXT` означает preview; неизвестное значение — ошибка. CI всегда передаёт контекст явно. `import.meta.env.PROD` не заменяет этот контракт.
- При preview без домена отсутствуют canonical, `og:url` и sitemap; присутствует noindex. При staging URL разрешены его метаданные, но индексация остаётся выключенной. Production требует реальный HTTPS SITE_URL.
- Источник контактов и правила готовности едины для валидатора и UI. Дубликат правил в нескольких файлах не допускается.
- Production требует минимум один контакт, утверждённые тексты и 3–6 реальных кейсов по ТЗ; отсутствие обязательных материалов даёт понятный отказ сборки. Изменить состав публичной версии можно отдельным решением пользователя.
- Fixtures валидатора проверяют положительные и отрицательные сценарии в изолированном временном каталоге. Тестовые контакты не попадают в `src/data` или артефакт публикации.

## 7. Задачи для выдачи агентам

### T00 Инвентаризация и сохранение исходников

**Владелец:** оркестратор. **Зависимости:** нет.

Проверить Git, существующие инструкции и материалы. Зафиксировать исходный список файлов и безопасную копию прототипа. Создать рабочую ветку `codex/total-stream-landing` при начале реализации. Если нужен исходный коммит для изоляции, добавить только выбранные файлы проекта; не захватывать случайные архивы и пользовательские материалы.

**Выход:** `docs/reports/T00.md` с инвентаризацией, выбранным способом сохранения и размещением приложения. **Приёмка:** исходники сохранены, способ восстановления понятен, ни один файл не потерян. Задача не включает перенос фиктивного контента в новый сайт.

### T01 Каркас и контракты

**Владелец:** оркестратор. **Зависимость:** T00.

Создать минимальный Astro-проект с TypeScript и статическим выводом. Зафиксировать совместимые стабильные версии Node/pnpm/зависимостей на момент начала реализации. Добавить команды dev, check, build, format:check и основу проверок. Создать `docs/contracts.md`, типы данных, список props и правила контекста сборки из раздела 6. Документировать запуск в README.

До реализации полного валидатора установить минимальный guard в `scripts/validate-release.mjs`: разрешать preview, отклонять неизвестный контекст и production с отсутствующими доменом/контактами. После T01 передать этот файл T03 для расширения. Источник настроек и способ чтения данных guard должны соответствовать контракту, без второй параллельной реализации правил.

Подготовить изолированный стенд в `tests/component-preview/` с отдельным root/outDir и тестовыми данными для заполненных карточек, длинных строк, контактов и пустых состояний. Команды стенда отделить от основного build. Оркестратор подключает к нему компоненты T02/T04/T05 по мере готовности; исполнители получают URL и могут проверять свою вёрстку до T07. Fixtures и страницы стенда не копируются в основной dist/ и не становятся публичными маршрутами. Предусмотреть проверку этого исключения при сборке.

**Выход:** собираемый каркас, lockfile, контракт версии 1, отдельный стенд и `docs/reports/T01.md`. **Приёмка:** чистая установка по lockfile, `pnpm check` и явная preview-сборка проходят; production пока корректно отклоняется при отсутствии обязательных данных. Стенд запускается отдельно и не попадает в публичный build. Нет React, серверного адаптера и маршрутов заявок. Исполнители получили контракт и не должны угадывать структуру props.

### T02 Дизайн-система и фирменные компоненты

**Владелец:** агент интерфейса. **Зависимость:** T01.

Реализовать tokens, typography, global CSS, Container, ButtonLink, SectionHeading и фирменный SVG-декор. Использовать первый концепт PDF. Временные значения палитры и fallback-шрифты пометить в отчёте. Подготовить композиционную схему desktop/mobile и показать компоненты в локальном preview; временная демонстрационная страница не входит в публичный build.

**Выход:** переиспользуемые компоненты и `docs/reports/T02.md` с изображениями состояний. **Приёмка:** кириллица, фокус, контраст, размеры нажатий, grid, отступы и типографика проверены; оркестратор принимает основу перед T04/T05. Работа с отсутствующим финальным шрифтом не выдаётся за финальную визуальную приёмку.

### T03 Данные и проверка готовности выпуска

**Владелец:** агент контента. **Зависимость:** T01.

Реализовать схемы и единый слой контента по контракту. Создать `docs/content-register.md` со статусами «утверждено», «черновик», «отсутствует». Подготовить черновые тексты без вымышленных обещаний, корректные пустые состояния и валидацию release-данных. Учесть источник и право использования каждого медиа. Нужные изменения package scripts передать оркестратору.

**Выход:** данные/схемы, валидатор, содержательные тесты в `tests/validation/`, `docs/reports/T03.md`. **Приёмка:** preview без домена и контактов собирается; production без них падает с объяснением. Проверены неизвестный контекст, ошибочные URL, отсутствие кейсов и демонстрационные материалы. Положительный тест использует только изолированные fixtures. Отсутствующие реальные материалы не блокируют завершение инфраструктуры контента.

### T04 Первый экран, навигация и контакты

**Владелец:** агент интерфейса A. **Зависимость:** T02; данные подключаются по контракту T01.

Создать SiteHeader, Hero, Contacts, SiteFooter и модуль мобильной навигации. CTA ведут к существующим якорям, меню раскрывается в потоке страницы, контакты формируются только из props. Использовать статический постер и fallback, пока изображение не предоставлено. При отсутствии контактов — некликабельная preview-подпись.

**Выход:** компоненты, `docs/reports/T04.md`. **Приёмка:** desktop/mobile, Escape и возврат фокуса, выбор якоря, no-JS, отсутствие переполнения заголовков и наложений декора. Заполненные контакты проверяются только на изолированном стенде; данные сайта остаются без вымышленных контактов. Ни формы, ни фиктивных телефонов в основном preview. `index.astro` и общие конфиги не изменяются; запрос на подключение к стенду отправляется интегратору.

### T05 Услуги и содержательные секции

**Владелец:** агент интерфейса B. **Зависимость:** T02; данные подключаются по контракту T01.

Создать Services, Cases, Reliability, Process, FAQ, Trust, Reviews и локальные стили. Кейсы показывают задачу, работу и результат на главной. FAQ использует details/summary. Скрывать пустые необязательные блоки, а для пустых кейсов в preview сохранять целевой якорь.

**Выход:** компоненты, `docs/reports/T05.md`. **Приёмка:** на изолированном стенде проверены сетка 1/2/3 карточки, длинный русский текст, отсутствие необязательных полей и работа без JS; в основном preview — корректные пустые состояния до получения кейсов. Нет фиктивных ссылок «Подробнее», отдельных страниц кейсов и повторяющихся id.

### T06 Локальная подготовка поставки

**Владелец:** агент поставки. **Зависимость:** T01.

Подготовить параметризованные шаблоны Nginx, процедуры выпуска/отката, проверки HTTP и описание CI без привязки к ещё не выбранному провайдеру Git. Следовать deployment.md: staging, HTTPS, настоящие 404, shared-ресурсы, блокировка публикации, атомарное переключение и сохранение релизов. Пустые домены и пути сертификатов должны останавливать генерацию production-конфига.

**Выход:** `infra/`, `scripts/deploy/`, `docs/reports/T06.md`. **Приёмка:** проверка шаблонов и сценарий два релиза → откат в изолированной Linux-среде, если она доступна. При отсутствии среды указать непроверенные пункты, не заявлять прохождение nginx -t. Задача создаёт подготовленные инструменты, а не настраивает удалённый VPS. Правила среды не обходить через неподдерживаемые локальные аналоги.

### T07 Интеграция страницы и SEO

**Владелец:** оркестратор. **Зависимости:** T03, T04, T05.

Собрать index.astro через единый слой данных, подключить секции, layout, favicon, локальные ресурсы и режимы SEO. Создать 404, robots и sitemap для нужного окружения. Подключить reveal без скрытия основного содержания при сбое JS. Принять запросы на общие файлы от исполнителей.

**Выход:** целый локальный preview, `docs/reports/T07.md`. **Приёмка:** одна H1, нет битых якорей и ресурсов, все основные сценарии доступны, команды README воспроизводимы. Production-ограничения соблюдены. Локальная 404 проверяет страницу; HTTP-поведение Nginx проверяется отдельно в T11.

### T08 Независимая проверка

**Владелец:** QA, не являющийся единственным автором проверяемого кода. **Зависимость:** T07.

Добавить и запустить пользовательские E2E-сценарии: меню, Escape, якоря, реальные/отсутствующие контакты, FAQ, no-JS, reduced motion. Проверить скриншоты 360/390/768/1024/1440/1920, увеличение 200%, focus, контраст и axe. Проверить бюджеты ресурсов и три одинаковых мобильных прогона Lighthouse с медианой.

**Выход:** `tests/e2e/`, `docs/reports/T08.md`, артефакты проверок в `output/qa/T08/`. **Приёмка задачи QA:** отчёт содержит воспроизводимые дефекты, их серьёзность и доказательства; успешное завершение отчёта не означает отсутствие дефектов. Без staging замеры помечены локальными. WebKit не называется реальным Safari; недоступную ручную проверку устройства явно оставить на запуск.

### T09 Исправления и готовность preview

**Владелец:** оркестратор, исправления распределяются прежним владельцам. **Зависимость:** T08.

Назначить дефекты по путям, устранить их и получить независимую повторную проверку затронутых сценариев. Полный регресс повторять при изменениях общих компонентов, конфигурации или новых рисках. Не менять ожидаемое поведение теста ради устранения красного результата.

**Выход:** `docs/reports/T09.md` и состояние G1. **Приёмка:** чистая установка, check, format:check, preview-build и E2E проходят; нет критических/существенных дефектов поведения, контентных утечек и переполнений. Незакрытые ограничения финальных материалов и аппаратной проверки перечислены отдельно. Production без данных должен продолжать отклоняться.

### T10 Реальные материалы и кандидат на выпуск

**Владелец:** агент контента и оркестратор; финальные проверки — независимый QA. **Зависимость:** T09 и полученные материалы.

Подставить контакты, основной домен, 3–6 кейсов, изображения, согласованные тексты, логотип и разрешённые шрифты. Обновить реестр. Получить подтверждение фактов от владельца проекта, если оно ещё не дано; уже согласованное не запрашивать повторно. Пересобрать production из проверенного состояния.

До production-сборки оркестратор фиксирует все входящие в неё исходники и медиа в коммите. Собирать из чистого checkout или экспорта этого SHA; lockfile и ресурсы входят в зафиксированное дерево. Проверить отсутствие незакоммиченных изменений входных файлов и записать параметры сборки, включая публичный SITE_URL. SHA в манифесте должен описывать фактический код артефакта, а не последний произвольный коммит рабочего каталога.

Оркестратор назначает независимого QA на повтор E2E по финальному production-артефакту, ручную проверку реального Safari и мобильного устройства. Если устройство или доступная среда отсутствуют, пункт остаётся явно незавершённым до G2; G1 при этом сохраняется. Изменения финального контента передаются его владельцу; файлы шрифтов и глобальных стилей обновляет оркестратор или явно назначенный владелец.

**Выход:** production-артефакт с проверенным SHA и контрольной суммой, `docs/reports/T10.md` с результатами независимого QA. **Приёмка:** финальная типографика и медиа проверены, контактные ссылки верны, нет noindex, preview-URL, заглушек, стенда компонентов и тестовых fixtures. Повторные E2E, Safari/мобильное устройство, затронутые визуальные сценарии и бюджет загрузки проверены. Без материалов или необходимой среды — `waiting_external` только у соответствующей задачи выпуска.

### T11 Подготовка VPS и staging

**Владелец:** агент поставки. **Зависимости:** T06, T09, предоставленные VPS/DNS/домены и поручение на настройку.

Применить конфигурацию на выбранной инфраструктуре по deployment.md. Настроить доступ, HTTPS, продление, staging с Basic Auth, кеши, MIME, логи и резервную копию конфигурации. Развернуть preview и проверить Nginx, два релиза и откат. Не публиковать публичный production в этой задаче.

**Выход:** рабочий staging и `docs/reports/T11.md`. **Приёмка:** nginx -t, 200/404, перенаправления, старые хешированные ресурсы, защита staging и процедура восстановления проверены на сервере. Недоступность VPS не отменяет выполненные T06 или G1.

### T12 Публичный выпуск и передача

**Владелец:** оркестратор с независимым проверяющим. **Зависимости:** T10, T11 и поручение на публикацию.

Проверить G2: все обязательные данные, финальные проверки и инфраструктура готовы. Опубликовать проверенный production-артефакт по процедуре выпуска, проверить основной HTTPS-адрес, контакты, SEO и сохранность предыдущих ресурсов. При сбое вернуть предыдущий релиз. Настроить предусмотренный мониторинг, когда канал уведомлений предоставлен.

**Выход:** `docs/reports/T12.md`, release-id, ссылка на сайт и инструкция владельцу. **Приёмка:** G3 подтверждён фактическими проверками, записан предыдущий релиз и ответственный за эксплуатацию. При первом запуске, когда предыдущего релиза ещё нет, описать процедуру снятия неудачного первого выпуска вместо заявления о несуществующем откате. Сам план не является поручением выполнить эту задачу сейчас.

## 9. Формат отчёта и приёмка

В `docs/reports/TXX.md` указать задачу, автора, время, исходный коммит или снимок, изменённые файлы и поведение. Далее — команды проверок с итогом, пути скриншотов/логов, найденные дефекты, внешние ограничения и требуемые изменения контракта. Если проверка не запускалась, писать «не выполнено» с причиной.

Оркестратор читает diff только назначенных изменений, проверяет соответствие контракту и воспроизводит необходимые команды. После приёмки фиксирует результат на доске и передаёт владение файлами следующей задаче. Для работы через Git интегрируется конкретный коммит; для общего workspace фиксируется набор файлов/контрольных сумм, чтобы было понятно, какую версию проверяли.

Изменение контрактов проходит через оркестратора: записать причину, обновить типы и описание, уведомить всех потребителей, назначить миграцию и повторные проверки. Пользователь нужен для изменения продуктового объёма или отсутствующих обязательных материалов; технические детали в согласованных границах решаются внутри команды.

## 10. Возобновление работы

После перерыва читать доску, актуальный Git status и отчёты активных задач. Проверить, работают ли прежние исполнители, прежде чем повторно назначать их файлы. При незавершённом изменении сохранить его и восстановить точку продолжения по отчёту; не начинать заново и не сбрасывать пользовательские правки.

При продолжении реализации брать следующую доступную задачу из доски. Статус done требует фактического результата и отчёта о проверках.
